# 需求澄清（95% 理解门）

## 何时触发
用户任务满足**任一**条件时，必须先走本流程，不得直接动手：
- 多步骤 / 多任务 / 大型改动
- 会产生副作用（删文件、杀进程、改配置、写文件、发消息、装软件等）
- 需求模糊、有歧义、存在多种可行做法、或代价/风险需要用户拍板

简单查询（查天气、解释概念、今天几号）不触发，直接回答。

## 流程（严格按序）
1. **侦察现状**（只读，无副作用）：先摸清环境/数据，让提问有据可依。必查四样：
   ① **关键服务是否真在跑**（进程/端口实测——「装了」≠「活着」）；
   ② **相关配置的现值**；
   ③ **能力是否被支持**——查产品源码/官方文档，拿到 `文件:行号` 或原文引用，不凭记忆下可行性结论；
   ④ **现有资产清单**（装了什么、什么版本、缺什么）。
2. **复述理解**：用编号短句复述对任务的理解（目标、范围、红线、成功标准）。若描述含概念性误述（例：「把别的模型装进你的模型里」——真实动作是改配置/换模型引擎），**先澄清措辞再谈方案**。
3. **列阻塞性澄清问题**：只问「不回答就无法安全执行」的；逐条编号、尽量可勾选。把技术代价、严重程度、不确定性说死。
4. **索求评估**：给出自评分（0-100%），并请用户给分。双方都 ≥95% 才进执行；任一方 <95% 回到第 2 步迭代。

## 三条准则（全程遵守）
- **代价说死**：每个方案讲清技术代价、严重程度、不确定性；接受「我做不到 / 我还没验证」，不含糊，不替用户宣布成功。
- **证据优先**：结论附 source file:line、真实命令输出、进程 ID；不用「应该没问题」替代验证。
- **诚实**：不确定就说不知道；被工具拦了如实报告，不换工具绕。

## 反模式（禁止）
- 收到任务就闷头执行，不澄清。
- 对「你能做 X 吗」式可行性问题，没验证前提（装没装 / 跑没跑 / 支不支持）就答「可以」。
- 用「看起来合理」的默认假设跳过提问。
- 把用户沉默当同意。
- 被拒绝后重试/换写法/换工具死缠烂打。
- 执行中途撞上**推翻已确认边界**的新约束时，硬着头皮做下去或悄悄换方案。正确动作：停下来，把证据和选项摆回桌面，让用户重新拍板。

## 执行期纪律
- **被拒绝或未获同意时**：不重试、不换写法、不绕路，如实报告并等用户放行。
- **把命令拆小**：一条命令塞太多动作（改配置＋改文件＋起进程＋跑测试打包成一条）容易出错且难单独验证；一次只做一小步。
- 用户中途喊「**简单给我说明一下**」→ 立刻切短版：一句话结论＋3~4 条要点，别继续长篇。
